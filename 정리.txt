● 세부 공통 해결방안

1. 클라 1은 상관없다. 클라 1은 일반적인 네트워크 루프( 실행 -> 네트워크 접속 -> ID 할당 -> 로컬 플레이어 생성 -> 리모트 플레이어 생성(안됨) -> 네트워크 루프의 순서로 간다.

2. 클라 2부터는 실행 -> 로컬 플레이어 생성(아이디 안받은상태) -> 리모트 플레이어 생성(없음) -> 아이디 할당 -> 네트워크 루프 순으로 진행되어 터지는것이다.

3. 이를 해결하기위해 서버에서는 클라가 접속한 순서대로의 ID를 부여했고, 서버는 이 아이디를 받기 전까진 패킷을 대충 넘기기만 하는, 임의의 큐(디퍼드 큐)를 만들어 프레임을 하나 미뤄서 패킷을 받았다.

4. 이로 각 클라이언트마다 자기 자신의 렌더링, 서로의 좌표패킷 수신까지는 되었다.

5. 이제 서로 좌표패킷을 기반으로 리모트 플레이어 생성을 해야하는데 이것이 안되었다.

현재 가장 최신분기


문제점

1. CLIENT_ID 수신 누락 또는 처리 순서 문제
클라이언트가 고유 ID (ClientNum)를 받기 전에 PLAYER_UPDATE, PLAYER_CREATE 패킷을 먼저 처리

이로 인해 자기 자신을 RemotePlayer로 생성하거나 자신의 캐릭터가 안 보임

결과적으로 ID 충돌, 동기화 실패 발생

2. PLAYER_UPDATE가 자기 자신에게도 전송됨
서버에서 PLAYER_UPDATE를 모든 클라이언트에게 브로드캐스트함

자기 자신도 포함되어 좌표가 다시 (0,0,0) 등으로 덮어써짐

특히 SendPacket()보다 PLAYER_UPDATE 수신이 먼저 되면 매 프레임 리셋됨

3. FrameAdvance() 내 player 생성 타이밍 문제
렌더링 도중 CreateLocalPlayer() / CreateRemotePlayer()가 호출되면서

D3D12의 commandList, device 등이 아직 초기화되지 않아 _com_error, abort() 발생 -> 이것은 코드꼬임에 의한 일시적 오류로, 작업에 직접적인 문제를 주지는 않음

4. 서버에서 syncDataMap.at() 호출 시 key 없음 → abort()
존재하지 않는 클라이언트 ID를 접근하면서 std::out_of_range 예외 발생


해결 시도 과정

CLIENT_ID 수신 이후에만 pendingPlayerCreates 처리

CreateLocalPlayer() 내부에 scene, commandList, device 체크 방어 코드 삽입

ServerSyncManager::GetPlayerSyncData()에서 .at() → []로 변경 + 존재 로그 출력

PLAYER_UPDATE가 자기 자신에게 전송되지 않도록 서버 수정

SendPacket()에서 좌표가 (0,0,0)이어도 전송 허용하도록 정책 조정



현재 상태


클라이언트 ID 수신 (⚠️ 불안정) - ClientNum 설정 전에 패킷이 들어오면 여전히 문제 발생
로컬 플레이어 생성(⚠️ 불안정) - 여전히 내 자신이 렌더링 안되는 상황 발생
RemotePlayer 등록(	⚠️ 조건문 중복 가능) - 일부 조건에서 이중 생성될 수 있음
패킷 처리 순서(⚠️ 위험) - 순서 꼬일 가능성 존재 (SendPacket < PLAYER_UPDATE)
